# Architecture and workflow

## Components

Corvex separates the request path from model and repository work:

1. **Server** exposes a GitLab Note Hook and authenticated agent endpoints. It verifies webhook secrets, applies the optional user blocklist, records events in SQLite, and replies to GitLab. The agent console discovers projects and branches through the configured GitLab read token.
2. **SQLite** is the durable queue and state store. It records events, webhook idempotency/delivery, attempts, audit events, conversations and their messages/turns, model call metrics, and optional daily token reservations.
3. **Worker** polls the database, claims an event under a renewable lease, records heartbeats for agent console monitoring, fetches the merge request head or Issue snapshot and repository, and runs the requested workflow. A worker requires `agent.enabled: true`. Conversation turns are not events and are executed inline by the Server instead.
4. **GitLab API** provides project/MR metadata, paginated diffs, and the destination for notes and discussions.
5. **OpenAI-compatible model API** is called by the worker for review, merge-request chat, explanation, fix proposal, or Issue implementation tasks, and by the Server for inline conversation turns.

GitLab GET requests retry transient network failures and HTTP 408, 425, 429, 500, 502, 503, or 504 responses up to three attempts with bounded backoff. POST writes are never automatically retried because their remote outcome may be uncertain.

Worker events also persist retries for transient HTTP/network failures and event timeouts before publishing. The delay starts at 2 seconds, doubles per attempt, and is capped at 30 seconds; the three-attempt event limit still applies. Authentication, validation, cancellation, stale snapshots, and publishing failures are not automatically retried.

The server can run without a worker: commands are accepted and persisted, but model tasks remain queued. In a split deployment the server and worker must use the same SQLite database and persistent Git storage root.

## Request and queue workflow

1. GitLab sends a `Note Hook` to `POST /webhooks/gitlab`.
2. The server compares `X-Gitlab-Token` to the configured webhook secret using a constant-time comparison. It accepts merge-request and Issue notes, limits the body to 1 MiB, and ignores system notes.
3. User IDs on `gitlab.blocked_user_ids` are rejected. Any other commenter on a project configured with the shared webhook secret can invoke a slash command or send plain text addressed to `@<gitlab.bot_username>`; register webhooks only where commands are intended.
4. Supported commands are parsed. The event, response-delivery state, audit event, and (for asynchronous work) the event itself are written transactionally to SQLite. Duplicate webhook deliveries are idempotent.
5. The server posts an immediate acknowledgement or validation response to the MR using the GitLab write token. Model inference does not run in the webhook request.
6. A worker claims queued review, explain, chat, fix, or implement events in creation order. It updates event status and attempt records while holding a renewable 30-second lease, and refreshes its heartbeat while idle and processing work.

The currently supported commands are `/review`, `/explain <path>`, `/fix [request]`, `/status`, and `/cancel` on MRs. Plain text after the bot mention starts a chat about the current MR or an assistant task on an Issue. Issue tasks include recent non-system comments and let the model reply, ask for clarification, or propose implementation. Code writes require `issue.implement_enabled: true`; `/implement [request]` remains available as an explicit implementation request. See [Getting started](./guide) for examples.

## Persistent conversations

The authenticated agent console uses the GitLab read token to search all visible projects and their branches. A conversation is a general chat bound to one repository branch; the server resolves and pins the branch head SHA when a turn is queued, and turns and assistant replies are persisted in SQLite and serialized per conversation. Conversations live in their own tables (`conversations`, `conversation_messages`, `conversation_turns`) and never enter the event queue: the Server executes each turn inline through `ConversationRunner`, so a conversation turn is not an event and does not appear in the events list. Each turn still keeps its own trajectory and execution records, stored against its `turn_id`; the console reads the whole conversation through `GET /api/ops/conversations/<id>/turns`, which merges every turn's trajectory and execution records into one timeline, or a single turn through `GET /api/ops/conversations/<id>/turns/<turnId>`, which verifies the turn belongs to that conversation, and aggregates usage and timing through `GET /api/ops/conversations/<id>/stats`; the detail response (`GET /api/ops/conversations/<id>`) also derives and returns the conversation's system prompt so the console can show it. Conversations are the console's primary object: the page fills the viewport with a conversation sidebar and a workspace whose **Chat**, **Call records**, **Trace**, and **Stats** tabs show the transcript (including each assistant reply's tool calls) with the conversation's system prompt above it, the execution records of every turn, one merged trace of every turn (switchable to a single turn), and the conversation totals. After the first turn completes, Corvex asks the model for a short title from the opening request and stores it on the conversation, so the sidebar lists conversations by that generated title (falling back to the project name before it exists); title generation is best-effort and never fails the turn. Each conversation carries an explicit mode (`ConversationMode`); only `read_only` exists today, and it is shown as a tag in the sidebar and repository header. Inline execution derives repository capability from that mode: `read_only` uses read-only repository tools and does not publish to GitLab. Each conversation keeps one read-only worktree reused across its turns (a follow-up on the same pinned snapshot only re-verifies HEAD instead of checking out the tree again), and idle worktrees are evicted by TTL and a cache limit and removed on Server shutdown. It runs in the Server process today and can later move to a container without changing this contract. If the branch moves before a queued turn starts, that turn ends as `stale` instead of answering from a mismatched snapshot. While a turn runs, the Server also streams the assistant text to the console over SSE (`GET /api/ops/conversations/<id>/turns/<turnId>/stream`): each event carries the cumulative text of the current model round (a new round resets it after tool calls), a comment heartbeat keeps the connection alive during tool execution, and a final `done` closes the stream as soon as the answer is persisted. The same stream carries each thinking sequence as `thinking` events and each tool execution as `tool` events. The console renders them as one interleaved timeline above the answer: every model round starts a new thinking entry, followed by the tool calls it triggered, so each thought and each tool call is visible separately. Thinking is never stored in SQLite. The transcript therefore fills in token by token instead of waiting for the whole reply, while the stored message remains the source of truth after the turn ends. The whole timeline stays expanded and cannot be collapsed while the turn runs, then collapses as one unit once it settles (the operator may expand it again); the chat pane is the single scroll container so the visible transcript uses the full workspace height.

### Context budgets

Corvex keeps a conversation inside the model's context window instead of letting the provider reject it. Before a request leaves the process, `src/agent/budget.ts` estimates tokens conservatively (the larger of chars/4 and UTF-8 bytes/3, so CJK and dense code are not undercounted) and `trimHistory` keeps only the newest earlier turns that fit `agent.history_token_budget` and the remaining `agent.max_input_tokens`; the dropped turns are compressed into a persisted rolling summary (`conversations.summary`) that later turns reuse, summarized in budget-sized chunks so the summary request cannot overflow on a long conversation. The request itself is built as structured messages rather than one concatenated blob.

Within a turn, tool results are truncated deterministically before they enter session history: `src/agent/tool-budget.ts` caps each call (about 32 KiB) and each assistant round (about 64 KiB) for a 128K window and leaves a marker telling the model to continue with a narrower path or line range. That hard cap matters because the SDK anchors its estimate on the last provider usage and can only estimate what was added since; an unbounded tool result could cross the window before the next compaction check. `agent.turn_tool_result_bytes` stays a soft checkpoint that asks the model to record progress and use targeted reads; the runtime caps it at four tool-output rounds so it fires before compaction. Context growth is absorbed by SDK compaction (the Pi session gets the same `agent.context_window` and compaction thresholds through an in-memory settings manager), and the reserve is raised to cover the worst-case token growth of one tool-output round plus `max_output_tokens`. If the provider still reports an overflow (`context length exceeded` and similar), `isContextOverflowError` recognizes it and one more aggressive retry drops the history entirely. These keys, plus the model name, response language, tool switches, review limits and repair permissions, are editable at runtime from the console Settings page. The Server validates them against the same definitions it uses for the config file, stores only the overridden keys with the operator and timestamp, records an `update_settings` audit entry, reapplies them at startup, and the Worker reloads them each poll and rebuilds the workflows that captured review limits in their constructor. The page returns an `effective` map computed with the same resolve functions as the runtime, so an entered value that is overridden by a safe floor is shown as such instead of looking ignored.

## Review workflow

1. Fetch the MR and check that it is open and still has the Head SHA captured when the request was queued. A closed or changed MR is marked stale rather than reviewed at a moving revision.
2. Update or create a per-project Git mirror, then create an isolated detached worktree at the exact Head SHA. The worker obtains the diff against the MR Base SHA and enforces the configured file and byte limits. Files within `review.max_files` are reviewed in batches of at most 10 files, further reduced as needed to fit `review.max_context_bytes`.
3. Send bounded MR metadata and each diff batch to the configured model endpoint. Corvex expects one structured JSON response per batch and aggregates usage and findings across the review.
4. Validate each response before publishing: findings must refer to an exact changed path and added line, include evidence found literally on that line, use a supported severity, pass size limits, and not duplicate an existing finding fingerprint. Findings are deduplicated and capped across all batches by `review.max_findings`. Corvex checks successful file-read traces for every batch, including batches with findings, and makes one targeted follow-up for unread files. If files remain unread, valid findings are published with a partial-coverage warning; a review with no findings fails rather than claiming complete coverage. Files omitted by configured limits are also reported as partial coverage.
5. Fetch the MR again. If its state or relevant diff SHAs changed while the model was running, mark the event stale and do not publish its result.
6. Publish supported findings as line discussions. If GitLab rejects an inline position, include that finding in the summary note instead. Clean up the worktree.

The model is not told that tests were run; Corvex does not execute project tests or repository scripts.

## Chat, explain, and fix workflows

**Chat** sends the bounded diff, pinned MR metadata, and the configured number of most recent non-system MR comments with the caller's natural-language request. The `read_mr_comments` tool can retrieve more comments from the current MR only. Chat can also use `git_log` and `git_show` to read commits reachable from its pinned MR HEAD; details require a full SHA. `update_mr_metadata` changes only explicitly requested title/description fields on the current MR and records the operation without storing their contents in the execution trace. When a write token is configured and the MR source project equals its target project, Chat receives bounded `git_status`, `git_apply_patch`, `git_commit`, `git_push`, and `git_revert` tools. They are bound to the task's isolated worktree and MR source branch; no shell or arbitrary command tool is exposed. Patch application is limited to existing tracked regular files, commits accept unstaged tracked modifications only, pushes require the remote branch to match the pinned or task-pushed SHA and use normal fast-forward semantics, and rollback adds a revert commit for the latest Corvex commit. For code-change requests, Chat completes all edits and available checks first, creates the final commit, then pushes as its last repository operation before replying; it does not push intermediate work or modify files after pushing. Fork MRs receive no Git write tools. Force-push is never available. These operations are audited without recording patch contents or credentials. Git output and comments are untrusted input. When the context byte limit is reached, older comments are omitted first. After a push, the worker verifies the live MR head equals the exact pushed SHA before publishing the response as a normal MR note. Chat does not create line discussions.

**Explain** reads the requested file from the pinned MR Head SHA, not from an arbitrary path on the server. Workspace containment and configured context limits are enforced. The file and MR metadata are sent to the model, then the explanation is published as an MR note only if the MR snapshot is still current.

**Fix** is disabled by default and follows the optional `gitlab.blocked_user_ids` rule as other commands. The worker sends the bounded MR diff and optional request to the model, accepts only a structured unified diff, and restricts changes to reviewable files already present in the MR diff. It applies the patch in the isolated worktree and runs `git apply --check` and `git diff --check`. After another MR snapshot check, it posts the proposed patch for a human to inspect and apply.

Fix mode does not execute tests, scripts, hooks, or other repository code. It does not create commits or push to GitLab. A posted patch is a proposal, not a verified change.

**Issue assistance** follows the optional user blocklist. Any ordinary bot mention on a project configured with the shared webhook secret queues an assistant task; the model receives the Issue and up to `issue.history_comments` recent non-system comments (default 20, range 0–50; comment context also has page and byte caps). It can reply or request clarification without publishing code. `issue.implement_enabled` is a separate, default-off write gate: when enabled, an explicit implementation request can produce a bounded unified diff. The project default branch is the target unless the current request explicitly names another existing branch; comments cannot authorize a branch change. The worker pins that target's base SHA, validates the patch (regular text files only; no traversal, Git metadata paths, symlink parents, binary content, renames, or mode changes), and rechecks the Issue and target SHA before pushing a new `corvex/issue-*` branch and creating a Draft MR. It never runs project scripts/tests, auto-merges, or closes the Issue. Publishing is not automatically retried when the remote outcome may be uncertain.

## Event states, leases, retries, and cancellation

The main lifecycle is:

```text
queued -> preparing -> analyzing -> publishing -> completed
                              \-> fixing -> verifying -/
```

Events can also end as `failed`, `stale`, or `cancelled`. The worker polls at `worker.poll_interval` and bounds an event with `worker.event_timeout`.

The 30-second lease is renewed while a worker is active. If a process disappears before publishing, an expired lease can return the event to the queue; interrupted events have at most three attempts. Classified transient failures and event timeouts are also returned to the queue with persisted backoff. Other processing errors are recorded as failed. If an event fails during publishing or its lease expires there, the outcome may be uncertain, so Corvex does not automatically retry and risk duplicating comments.

`@<gitlab.bot_username> /status` reports the latest task on the MR. `@<gitlab.bot_username> /cancel` immediately cancels a queued task or asks the worker to stop an active task. Only the task requester can cancel it. Cancellation is not available after the task has entered publishing, where GitLab may already have accepted a comment.

## Persistence and retention

SQLite uses WAL mode, a single open connection, and a 5-second busy timeout. Keep the database on persistent writable storage. Daily cleanup removes old terminal events, their attempts, webhook event records, and token usage according to `storage.retention_days`; audit records use `storage.audit_retention_days`. Queued and in-progress events are retained. Git mirrors and worktrees are stored separately under `storage.root` and require their own capacity monitoring.

## Security boundaries and limitations

- The webhook secret authenticates GitLab deliveries; the optional user blocklist restricts which users can request work.
- Register the webhook only on projects where Corvex should accept commands. The agent console project scope is the set of projects visible to its GitLab read token; it is not controlled by a static project allowlist.
- Use a read token for API/repository reads and a separate write token for MR comments. Do not give the service the administrator token used by the optional hook-registration script.
- Repository content, comments, filenames, and fix instructions are untrusted model input. Model output is validated, but validation is not a substitute for human review.
- Model prompts may contain source code and MR text. Review the model provider's data handling and your organization's policies before enabling it.
- The worker does not run untrusted repository code. There is no test runner or automatic patch application to the target branch.
- The HTTP service implements GitLab merge-request Note Hooks, not push hooks or merge-request lifecycle events.
