# AGENTS.md

Guidance for coding agents working in this repository. Read `design.md` before making architectural changes: it is the binding contract for the runtime, boundaries and security invariants.

## Project overview

Corvex is a self-hosted GitLab collaboration agent. It is a single TypeScript application running one process that owns one SQLite database and one Git storage root:

- `server`: the only runtime mode. It serves the ops console and executes conversation turns inline through `ConversationRunner`. The ops console authenticates each user through GitLab OAuth2 and discovers projects visible to that user.
- `ConversationRunner` (in-process): claims a turn, pins the repository branch head SHA, reuses the conversation's detached Git worktree, runs one Pi SDK session for that turn, streams its output, and persists the trajectory and final reply. Startup recovers interrupted turns.

The agent runtime is `@earendil-works/pi-coding-agent` (Pi SDK). Pi runs the model loop, tools and skills; Corvex owns authorization, state, validation and GitLab writes. Conversations live in their own `conversations` / `conversation_messages` / `conversation_turns` tables and run inline in the Server. Webhook-driven task events are deferred; see `ROADMAP.md`.

The composer keeps a per-conversation input history in `localStorage` (`src/app/ui/inputHistory.ts`): Up/Down navigate older/newer messages only when the caret is on the first/last line, preserving multiline editing, and Down from the newest restores the in-progress draft. Active conversations offer grouped quick prompts above the composer, and the composer completes slash commands (`/review`, `/explain`, `/fix`, `/test`, `/docs`, `/commit`, `/mr`) parsed by `src/app/conversation-command.ts`. These are turn-local model instructions only — they never create events, change state, or publish; titles strip the command prefix.
Conversations are the ops console's primary object: a conversation binds one repository branch and each turn keeps its own trajectory (`conversation_trace` keyed by `turn_id`) and execution records. The console opens on Conversations, renders each assistant reply's thinking and tool calls in the Chat tab through `ConversationTimeline`, syntax-highlights fenced code blocks in replies with `MarkdownCode`/`highlight.js` injected through XMarkdown's `components.code` (inline code stays plain, dark theme overrides live in `theme.css`), shows the conversation's system prompt above the transcript (the server derives it from `agent.response_language` and the conversation mode in `GET /api/ops/conversations/:id`), and reads a single turn's records through `GET /api/ops/conversations/:id/turns/:turnId`; the store verifies the turn belongs to that conversation. Trajectory data stays redacted and size-capped in `src/store.ts`.

The repository name above the conversation is a button that opens `RepositoryInfoPopover` (a click-triggered Ant Design `Popover` anchored `bottomLeft`, not a drawer) with GitLab project metadata from `GET /api/ops/projects/:id` plus the conversation's branch and pinned SHA; only http(s) `web_url` values become links. Because the popover is portalled to `body`, its content uses the global theme variables; the panel background/text, title color and 340px cap are set through `styles.container` / `styles.title` / `styles.root` with `var(--bg-panel)` / `var(--text)`, so both light and dark modes stay in sync with the console (Ant Design's runtime styles need at least four class selectors to override via CSS). The conversation sidebar groups conversations by repository with the most recently updated conversation (and group) first; each group has a sticky header with a stable color dot and separator, items are single-line titles, and a running turn shows a pulsing dot. Group headers toggle their conversations, and a button placed before the Chat tab in the workspace tab bar collapses the whole conversation list entirely; both states persist in `localStorage` and the width transition matches the main sidebar. Right-clicking an item opens archive/unarchive and delete actions (`POST /api/ops/conversations/:id/archive`, `DELETE /api/ops/conversations/:id`); archived conversations are hidden by default and reachable through a sidebar toggle. Deletion also removes the conversation's worktree and is rejected while a turn is running.

While a turn runs, the Chat tab streams its assistant text so the reply fills in token by token instead of appearing at once. `PiAgent` forwards cumulative text from the SDK's `message_update` events (`onTextDelta`), `ConversationRunner` publishes it per turn with the latest snapshot for late subscribers, and `GET /api/ops/conversations/:id/turns/:turnId/stream` serves it as SSE. The console reads it through `src/app/ui/stream.ts` with `fetch` rather than `EventSource`, because the console's Basic credentials are only attached automatically to same-origin `fetch`. The stream is display-only: it never writes to SQLite, closes with a `done` event as soon as the answer is persisted, and polling remains the fallback when the connection drops.

The same stream carries the model's thinking text as `thinking` events and each tool execution as a `tool` event. The console renders them as one interleaved `ConversationTimeline` above the final reply — a new thinking entry starts on every model round and the following tool calls are appended in execution order, so every thought and every tool call is visible separately. Thinking, intermediate replies and tool calls are folded into a redacted, size-capped process snapshot on `conversation_turns.process`, so the process block survives a reload; redacted thinking parts are skipped in the live stream and tool events carry a call ID for replay. The whole process block is forced open and cannot be collapsed while the turn runs, then collapses as one unit when it settles (the operator may expand it again). Each tool call is itself a small disclosure whose parameters stay hidden until expanded. For conversation tasks the `record_plan` tool records a bounded 3-6 step checklist without an extra model call; the Chat process block renders `record_plan` tool inputs as a numbered plan, and the plan is persisted in the process snapshot. A streaming thinking block (`ThinkingContent` in `ConversationTimeline`) follows new text only while its own scroll position is at the bottom; scrolling up detaches it, using `isAtScrollBottom` from `src/app/ui/scroll.ts`. Long tool-call descriptions keep their head and tail visible with a middle `...`: `fitMiddleEllipsis` measures real glyph widths via canvas and splits evenly, a `ResizeObserver` re-fits on width changes, and the summary wraps so status/duration/parameters never squeeze the name into a few characters; the full text stays in `title`. Context changes are first-class: `PiAgent` consumes SDK `compaction_start`/`compaction_end` (and Corvex's own history-trim retry), records `kind='context'` trace entries (`context.compact` / `context.trim`), and forwards localized notices through `onContextDelta` → SSE `context` → a `conversation-context-notice` segment in the Chat process block; the Trace tab shows context as a third track alongside LLM and tool. The context trace records bounded before/after snapshots: a `session_before_compact` extension captures the messages scheduled for summarization (`buildContextSnapshot`, capped by message/character count), and `compaction_end` stores the resulting summary and first kept entry id; Trace's Context inspector shows both snapshots. The observe extension also emits the start notice as soon as `session_before_compact` fires and reuses one id through success/failure; the start notice explains the trigger (reason, tokens/window percentage, effective threshold) from `session_before_compact`; after one SDK summarization failure it returns a deterministic bounded summary instead of letting the over-limit context trigger the same failing LLM summarization forever. The process uses a lightweight OpenCode-style timeline (left rail, per-step dots, small muted headings, single-line tool rows) rather than stacked cards. A right-side turn rail (`ConversationTurnNav`) shows every user-initiated turn as a slim vertical bar inside a fixed-height rail, so bars shrink as turns accumulate; bars are numbered by turn (matching the Trace tab, not the raw message index) and the rail is anchored 20px right of `.ant-bubble-list .ant-bubble-list-scroll-content` and vertically centered. Hovering shows the summary and date; clicking jumps to that turn. Wheel direction follows the platform: on Windows/Linux scrolling down advances to newer turns and up goes back; on macOS the mapping is inverted for natural scrolling. Each wheel step scrolls the transcript to that user message, and scrolling the transcript updates the active marker. The chat transcript pane is the single scroll container: `Bubble.List`'s internal scrolling is disabled and the pane follows new content only while the user is near the bottom; scrolling more than 160px away from the bottom reveals a floating `Scroll to latest` button that smoothly returns to the newest message (both the threshold and the button state are driven by `handleTranscriptScroll`). Switching workspace tabs or switching conversations always resets the transcript to the latest message, via a `forceScrollToLatest` ref consumed either by the scroll effect or by the pane ref callback when rc-tabs mounts a fresh Chat pane. While a turn is running or queued, the composer's suffix swaps the send button for a `Stop` button that posts `/api/ops/conversations/:id/turns/:turnId/cancel` and clears the local pending state. Desktop notifications are handled by the `useTurnNotifications` React hook (`src/app/ui/useTurnNotifications.ts`) plus the sidebar bell: the first send requests permission, the bell toggles the saved preference, and a turn-completion notification is only raised when the page is hidden or unfocused. A user can also interject while a turn runs: `POST /api/ops/conversations/:id/messages` routes the message through `ConversationRunner.interject` into a per-turn `SteerChannel` (`src/agent/pi.ts`) that binds `session.steer` once the Pi session is ready, so the supplement reaches the model before its next call without creating a new turn or changing the pinned SHA. Messages arriving before the session exists are buffered and drained in order (`setSteeringMode("all")`), and a turn that already settled falls back to a normal queued turn so input is never lost. The same endpoint keeps the idle path unchanged and also accepts `delivery: "queue"` (a durable, reorderable FIFO list in `conversation_followups` that the Runner drains after the turn settles, re-pinning the branch SHA per item and surviving restarts) and `delivery: "interrupt"` (abort the turn, wait for its partial changes to land, then start a fresh turn). The composer shows interject, queue, interrupt and Stop actions while a turn is active, plus a queue panel with reorder/remove. The workspace also has a read-only Git tab (`ConversationGitGraph` + pure `gitGraph.ts` layout): `GET /api/ops/conversations/:id/git/graph` reads the project mirror (`rev-list --parents --topo-order --all`, bounded by limit/offset), highlights the conversation's pinned SHA and `refs/conversations/<id>` commits, draws lanes/merges as SVG beside an antd `Table` (aligned Commit/Date/Author/Hash columns, sortable, with a legend and an author filter backed by `/git/authors` and the graph's `author` query), also resolves lightweight/annotated tags (dereferenced via `for-each-ref`'s `*objectname`, returned in each node's `tags` field and rendered as orange badges/dots), marks the worktree HEAD (and its current branch name when not detached) with a purple `HEAD` badge; the toolbar has Pull and Push-to-ref quick actions (`POST /api/ops/conversations/:id/git/pull` and `/push`, rejected while a turn is running) that fetch from the mirror or save worktree changes to the conversation ref; and expands the selected commit inline under its own row via `GET /api/ops/conversations/:id/git/commit/:sha` to show the full message and bounded patch with on-demand pagination; the SVG row offsets are recomputed from measured item heights so nodes and edges stay aligned with the list after expansion; when an author filter hides a commit's parents, the layout draws a dashed edge to the next visible commit so the history stays visually continuous. The same file list and diffs live in a standalone **Changes** workspace tab (the Git tab shows only the commit graph); both are backed by `GET /api/ops/conversations/:id/git/changes`: it diffs the conversation ref against its parent commit in the mirror and renders a bounded per-file patch list; each expanded patch is shown in a lazily loaded Monaco inline diff editor (`DiffViewer`, sharing `src/app/ui/monaco.ts` setup with `CodeViewer`), with `parseUnifiedDiff` reconstructing the two sides from the hunk and themes following the console theme. The same view can be filtered to one turn via `GET /api/ops/conversations/:id/turns/:turnId/changes`: each saved turn also writes a `refs/conversation-turns/<conversationId>/<turnId>` ref in the mirror so its diff is replayable independently. Deleting a conversation removes the worktree, the conversation ref and every per-turn ref; startup/daily retention prunes orphan refs the same way. The console's "discard changes" action asks for confirmation first, lists the affected paths and offers downloading a `git format-patch` patch before the irreversible deletion. Deriving changes from Git objects (not from recorded fs-write calls) is deliberate: future command-line or external edits will still be detected as long as they land in the worktree/conversation ref. Right-clicking a commit row opens a controlled `Dropdown` (1×1 anchor, outside-click/Escape to close) with copy hash/short hash/subject/author, download patch (standard `git format-patch` mailbox output via `GET .../git/commit/:sha/patch`, saved as `<short-sha>.patch` and directly applicable with `git apply`/`git am`), and "view details" actions. The floating composer starts at three rows (`autoSize`) and its `footer` holds `ComposerModelPicker`, which groups the provider catalog in a borderless `Select`; choosing a model calls the existing activate endpoint, so the switch is global and applies to the next turn (pure grouping/active lookup logic lives in `src/app/ui/modelPicker.ts`).

The welcome page's quick prompts come from `welcomePromptGroups(copy)` and render as grouped Ant Design X `Prompts` cards (a category heading plus two questions); clicking a child resolves the full question by key, and the setup pane never auto-scrolls to the bottom. The repository and branch selectors (`.conversation-composer-setup`) sit centered between the welcome text and the grouped prompts, while the floating composer's footer holds only the model picker.

Each conversation carries an explicit mode (`ConversationMode` in `src/model.ts`, default `gitlab`) instead of hardcoded assumptions. `conversationCapabilities(mode)` is the single source for a mode's workflow step, repository writes and GitLab writes; the runner, the Pi prompt and tool access, the store, and the console all derive from it. `src/agent/tool-catalog.ts` injects a `<available_tools>` section into the system prompt via the Pi SDK `before_agent_start` hook, built from `pi.getActiveTools()` and `pi.getAllTools()`: the SDK skips its own tools section when a custom systemPrompt is supplied, so without this the model only has function schemas and can deny having tools when asked. The static prompt tells the model that this section is the sole authority for capability questions (`src/agent/tool-access.ts` is the shared source for the web-tool switches used by registration). Conversations are uniformly read-write: `gitlab` (the only mode) reads the repository and adds the full bound GitLab tool set from `src/agent/gitlab/` (`issue.ts` and `merge-request.ts`, combined in `index.ts`): discovery/reads (`get_project_info`, `list_*`, `get_*`, `get_merge_request_changes`, paginated `get_merge_request_commits`, discussions), Issue lifecycle (create/update/close/reopen/delete plus note create/update/delete) and MR lifecycle (create/update/close/reopen/merge/delete, approve/unapprove, note create/update/delete, resolve discussions), repository file edits go through the bounded fs-write tools, and `gitToolset: true` also enables the consolidated `src/agent/git/` tool set (`inspect.ts`: git_status/log/show/diff/branches; `workspace.ts`: git_clone/branch/checkout/pull/merge (git_checkout switches to a local branch or tracks origin/<name> before an MR); `changes.ts`: git_commit/push/publish/push_branch/rebase/cherry_pick/revert; combined in `index.ts`). All Git tools are bound to the conversation's worktree and local project mirror: no arbitrary URL/remote/force option. `git_push` writes `refs/conversations/<id>` in the mirror; `git_publish` saves the current changes and fast-forwards the resulting commit to a named GitLab branch in one call (no SHA to remember), so a merge request can show a real diff. `git_push_branch` is the lower-level variant for an already known SHA. Both require explicit user request and never force-push. All GitLab tools are fixed to the conversation's project, iids must come from the user or a read result, and write tools require explicit user intent; irreversible or public actions (delete/merge/approve) say so in their descriptions. Adding a mode means extending `conversationCapabilities`, the prompt and tool wiring, then updating docs.

Each conversation keeps one worktree reused across its turns (`workspaces/<projectId>/conversation-<conversationId>`, derived by `conversationWorkspaceName`) instead of preparing and deleting one per turn. `ConversationRunner` owns the cache (idle TTL plus an LRU cap, released on Server shutdown and swept again on every startup so a crash cannot accumulate worktrees); `GitManager.prepareConversationWorkspace` re-verifies HEAD for the same pinned SHA and only `checkout --detach`s when the snapshot advanced, so the fixed-SHA invariant still holds. Conversations write to the worktree only through the bounded fs-write tools or the bound Git tool set, and are serialized per conversation, which is what makes reuse safe; branch/merge/rebase/cherry-pick/revert tools are validated; rebase/cherry-pick run only on a clean worktree and abort automatically on conflicts, and no tool force-pushes. Git mirrors are also fetched lazily: `prepareConversationWorkspace` runs `cat-file -e` first and only fetches the SHA when it is missing. `storage cleanup` skips conversation workspaces whose conversation still has a queued or running turn (`AppStore.activeConversationIds`), and keeps mirrors for any project referenced by a conversation (`AppStore.pendingProjectIds`) so a later follow-up does not re-clone the whole repository. The workspace TTL/cap and retention days are runtime settings editable in the ops console; eviction never touches queued or running conversations (a removed idle worktree is simply rebuilt on the next turn). Cleanup runs are recorded in `storage_cleanup_log` and shown, 10 per page, in the Storage tab of the Settings page, which is split into Basics / Model / GitLab / Storage / Advanced tabs. The Model tab manages model providers: each provider stores a name, Base URL and API key, and lists its models with their own context window and max output tokens; one model is active globally, the first model added is activated automatically, and selection is applied to the config on Server startup (legacy `model` / `model_base_url` / `model_api_key` runtime overrides are migrated into a provider, and the previous single-table `model_profiles` list is split into `model_providers` + `provider_models`). The API key is never returned by the API or written to audit logs (an empty password field keeps the saved value), so the SQLite file and its backups must be protected. Each settled assistant reply's actions row starts with the Copy button, followed by generation TPS, elapsed turn duration, and the producing model label. TPS and duration are computed in `AppStore.getConversation` from successful LLM traces (`generation_duration_ms`) and the turn's created/updated timestamps, so the Chat tab needs no extra request. The label uses the settings provider's display name (`applyActiveModel` copies it to `agent.providerName`) plus the model ID; the Pi SDK's internal `corvex-openai-compatible` provider ID is never shown (`displayModelName` strips it from older rows, in both the transcript and Trace).

## Environment

- Node.js 26.12.1 (`.nvmrc`, `engines.node`) and pnpm 12.4.1 (`packageManager`). Do not switch package manager or edit `pnpm-lock.yaml` by hand; keep the `allowBuilds` entries in `pnpm-workspace.yaml`.
- Install with `pnpm install --frozen-lockfile`.
- `git` must be on `PATH`: the inline conversation runner shells out to Git, and unit tests build real repositories.
- SQLite comes from Node's built-in `node:sqlite`. Never add a database driver, ORM or query builder.

## Code conventions

- ESM with `module`/`moduleResolution` `NodeNext`: relative imports carry a `.js` extension even from `.ts` files (`./model.js`). Use `import type` / `type` modifiers for type-only imports.
- TypeScript is `strict`. Avoid `any`; validate external data (YAML, HTTP bodies, GitLab payloads, model output, SQLite rows) at the boundary and narrow with type guards.
- Prefer Node built-ins (`node:fs/promises`, `node:crypto`, `node:sqlite`, `node:timers/promises`) and standard `fetch`. The HTTP layer uses Fastify (`src/app/http`: `server.ts` lifecycle plus `auth.ts`, `routes.ts`, `respond.ts` and per-area route modules), justified in `design.md`; it keeps every request body as a raw Buffer, `/api/ops` validates `content-type` and parses JSON itself, and SSE hijacks the raw response. Preserve the existing status codes, bodies, headers, auth realm and log keys when changing routes. New runtime dependencies are an architecture decision: justify them in `design.md` and keep the dependency set minimal.
- Source comments and JSDoc are written in Chinese; keep that convention and keep them true. Identifiers and user-visible log keys are English.
- User-visible text follows the configured `agent.response_language` (`en` or `zh-CN`). Docs are bilingual: `docs/<page>.md` plus `docs/zh-CN/<page>.md`, and `README.md` plus `README.zh_CN.md`, with navigation in `docs/.vitepress/config.mts`. Update both languages when behavior, config, or operations change.
- No secrets in code, configs, fixtures, logs, prompts or trace payloads. Trace data is redacted and size-capped in `src/store.ts`; do not bypass that path. `src/redact.ts` owns the shared rules (`redactSensitiveText`, `sanitizeSensitiveValue`, `sanitizeSensitiveText`): `startTrace`/`finishTrace` now sanitize pre-stringified `trace_input`/`trace_output`/`raw_content`/`error_detail` at the storage boundary (structural JSON redaction for stringified objects, text regex otherwise, then a 64 KiB cap), and `saveConversationSummary` redacts model-generated summaries. `buildContextSnapshot` redacts tool-result text before it can enter a compaction trace or the Trace inspector, and `PiAgent` redacts compaction summaries before reusing them as the cross-turn rolling summary.
- Each user also has a personal settings page at `#/settings` backed by `/api/ops/me/model-providers`. System providers (`owner_user_id = ''`) are shared and read-only there and carry a System badge; users can create/edit only their own providers and models, and activation writes a per-user `user_model_selections` row (never the global active model). `ConversationRunner` clones the runtime config and applies that selection per turn, so personal models never mutate shared state or leak across users. Both the admin and user model managers offer connection tests (`POST .../model-providers/test` probes `/models`, `POST .../model-providers/:id/models/test` sends a one-token chat completion); results never echo the API key and are implemented in `src/app/http/ops/model-test.ts`.
- The conversation workspace uses `react-resizable-panels` (`Group`/`Panel`/`Separator`) for three resizable panes: conversation list, workspace, and a right-side file panel toggled by an icon next to the pinned-revision text. All three have pixel min/max sizes, support keyboard resize and collapse, and persist their layout in `localStorage`; do not reintroduce hand-rolled drag handles. `ConversationFilePanel` is a tab container (currently only file browsing) so more tools can be added later. File browsing uses an adapter: `ConversationFileSource` in `src/app/files/source.ts`, with `LocalFileSource` as the **default** — it reads the conversation's persistent worktree under `storage.root/workspaces/<projectId>/conversation-<id>` through the shared `resolveWorktreePath` guard, so files edited by the agent are visible. `GitLabFileSource` (repository tree + file endpoints at the pinned SHA) remains available and is used as an automatic fallback when the worktree has been evicted or the first turn has not prepared it yet; both enforce the 200-entry / 256 KiB bounds. Swap the factory to add another source without changing routes or UI. Every tree/content result carries a `source` field (and the image route sets `x-corvex-file-source`) so the file panel can show a badge of which adapter actually served the read, including after a fallback. Images (png/jpeg/gif/webp/bmp/avif/svg/ico) are previewed through `GET /api/ops/conversations/:id/files/image`; `ConversationFileSource.readImage` validates magic bytes against the extension, caps bytes at 12 MiB, and the route serves raw bytes with `nosniff` plus an isolated CSP (the UI uses `<img src>` so the session cookie is attached). The viewer is the standalone `src/app/ui/components/ImagePreview.tsx`: it fits the image to the current container (max size = container), zooms with the wheel anchored at the cursor via a non-passive native listener, pans with pointer capture, and resets on double-click or the Fit button; ResizeObserver keeps the fit ratio in sync with panel resizing. Text files use the lazy-loaded `src/app/ui/components/CodeViewer.tsx` (Monaco, `readOnly` + `domReadOnly`) instead of a `<pre>`: languages come from the explicit extension map in `src/app/ui/language.ts` (including `.mjs`/`.cjs`/`.zsh`/`Dockerfile`) with a registered-extension fallback, full content is fetched with `?full=1` (still 256 KiB-capped), and matching `corvex-light` / `corvex-dark` themes follow `data-theme` via a MutationObserver, and Monaco's built-in English "Cannot edit in read-only editor" hint is overridden through its `readOnlyMessage` option with the app's localized copy (so it follows the same system/explicit language preference). It is a separate Vite chunk; do not import Monaco eagerly. Conversation file tools are split into `src/agent/fs/read.ts` (read-only, skill roots allowed) and `src/agent/fs/write.ts` (all mutations through one `WorkspaceFs` interface and shared `resolveWorktreePath` guard: `write_file`, `edit_file`, `delete_file`, `move_file`, `copy_file`). `edit_file` (exact old_string/new_string replacement) is preferred for small changes, `write_file` for full rewrites; all are bounded and worktree-relative only. Edits are NOT stored in SQLite or left in the disposable worktree: `GitManager.saveConversationChanges` commits them to `refs/conversations/<id>` in the project mirror (parent = pinned SHA); `prepareConversationWorkspace` checks out that ref when present, so TTL/LRU eviction, shutdown and startup cleanup can still delete worktrees without losing edits. `DELETE /api/ops/conversations/:id/changes` removes the ref and worktree; deleting the conversation does the same. `pruneHistory` deletes conversations via SQL, so startup and the daily retention task call `GitManager.pruneConversationChanges(validIds)` to remove orphan refs and `gcMirrors()` (`reflog expire` + `gc --prune`) to reclaim unreachable commit/tree/blob objects. All of these cleanup steps run through the `storageCleanup` hook with default taps at fixed stages (history prune → ref prune → mirror gc → idle workspace release → audit record); each tap isolates its own errors into the shared context. Never push these refs to GitLab.
- The console CSS runs through PostCSS with `postcss-nesting`: repeated long ancestor selectors are grouped with standard `&` nesting in the source; the built CSS stays flat so the specificity needed to override Ant Design is unchanged.
- The ops console runs on Ant Design v6. Select-like popups are portalled to `body`, so they leave the component's subtree: custom properties defined on the trigger do not reach them (pass `classNames.popup.root` and declare the popup's own variables), and Ant Design's runtime-injected styles use three class selectors, so overrides need at least four.
- The console page carries a nonce-based Content Security Policy, so never call static `Modal.confirm` / `message.*` / `notification.*`: they render outside `ConfigProvider`, their injected styles have no nonce and the browser drops them. Use `Modal.useModal()` (or `App.useApp()`) and render the returned context holder inside the page; `test/unit/ui-modal-context.test.ts` enforces this. Some rc-* utilities (notably scrollbar measurement) inject `<style>` tags without a nonce; `src/app/ui/csp.ts` runs first from `main.tsx` and stamps the page nonce onto dynamically injected style nodes instead of weakening `style-src-elem` with `unsafe-inline`.
- The console supports light and dark themes with a three-way preference (`system` / `light` / `dark`) persisted in `localStorage` under `corvex-ops-theme`; `system` follows `prefers-color-scheme` live via `matchMedia`. `src/app/ui/theme.css` owns all semantic color variables (`--bg-*`, `--border*`, `--text-*`, `--primary*`, status colors); `:root` holds the light palette and `[data-theme="dark"]` overrides it. `App` sets `document.documentElement.dataset.theme`, switches Ant Design with `theme.darkAlgorithm`, and exposes `ThemeToggle` in both the main sidebar head and the admin console; code-block token colors are overridden for dark mode. Console CSS must use these variables instead of literal hex colors (the public landing page is a self-contained dark marketing page and is exempt).
- The console shell (`.app-shell`) is a full-viewport flex row: a collapsible left sidebar (`<aside class="sidebar">`, `flex: 0 0 auto`) holds a compact head (48px: brand plus icon language/theme `Dropdown`s; language offers Follow system / English / 简体中文 and defaults to the browser preference, migrated from the legacy saved-locale key, while theme offers Follow system / Light / Dark) above the inline `Menu`, and a scrolling `<main>` (`flex: 1`, `min-width: 0`) fills the rest. Collapsing toggles `inlineCollapsed` and the `sidebar-collapsed` class (narrow width, icon-only menu, icon-only brand head, and the bottom account panel showing only the avatar) and persists in `localStorage`. There is no footer: the refresh caption is a floating `#updated` span positioned over the shell (hidden under 800px). Non-conversation pages keep their centered max-width via `<main>` padding (`max(24px, calc((100% - 1200px) / 2))`) with `overflow: auto`, so the scrollbar sits at the window edge; the conversation route adds `content-full`, which drops the padding and lets the workspace fill the whole `<main>`. On the conversation page the repository info is passed to the `Tabs` `tabBarExtraContent` so it shares the tab row (it wraps below the tabs under 640px) rather than occupying its own header line.
- The conversation **Trace** tab reads the whole conversation through `GET /api/ops/conversations/<id>/turns` (every turn's trajectory merged into one timeline) and defaults to that merged view; `GET /api/ops/conversations/<id>/turns/<turnId>` still serves a single turn. `TraceExperience` renders only the timeline (`TraceDiagram`); the earlier session view was removed, so keep one view rather than re-adding tabs. Trace entries and execution steps carry `turnId`, so the console groups them by turn. The timeline geometry lives in `buildTimelineLayout` (`src/app/ui/trace.ts`): each turn becomes one band with its own ruler and a fixed pixel `segmentGap` between bands, so real elapsed time is expressed by each band's own ruler and a long pause between turns does not open a huge blank. Because bands are laid out independently, drag selection compares absolute pixels, not the per-band ratios.
- Context governance lives in `src/agent/budget.ts` (`estimateTokens`, `estimateConservativeTokens`, `resolveMaxInputTokens`, `resolveHistoryBudgetTokens`, `chunkForSummary`, `isContextOverflowError`, `trimHistory`), `src/agent/tool-budget.ts` and the `agent.*` budget keys (`context_window`, `max_input_tokens`, `history_token_budget`, `turn_tool_result_bytes`, `compaction_*`, `summary_enabled`). Repository-file tools reject absolute worktree paths at the tool boundary (`requireRelativeRepoPath`; absolute paths are only accepted for trusted skill roots) and the system prompts require repository-relative paths, so worktree paths never leak into trajectories. Tool results are hard-truncated per call and per assistant round before they enter session history, and the compaction reserve still covers a **full** tool-result round plus `max_output_tokens` and a fixed margin; the round bound itself scales to 25% of the context window (4 KiB floor, 128 KiB cap), and an explicit `compaction_reserve_tokens` is capped at 25% of the window (default `0`, i.e. derived) so a 32k window compacts around 62.5% instead of 50% while still leaving room for a maximal tool round before the next request. `turn_tool_result_bytes` stays a soft checkpoint, not a hard cap: at 75% the model is steered to record progress and use targeted reads, but the turn is not aborted; context growth is absorbed by SDK compaction and a single history-dropping retry on a provider overflow. `session.prompt()` resolves normally when the provider rejects a request, so `runSession` records the final assistant message's `errorMessage` and rethrows it: without that, a failed turn would return the previous turn's reply (the last assistant message in the session) as a fresh answer and the overflow retry would never fire. Requests are trimmed locally before they leave the process; do not widen these budgets to paper over a provider error. `resolveMaxPromptBytes` derives the per-request prompt cap from `context_window` rather than a fixed 96 KiB, so long history is not rejected before it leaves the process. `src/agent/token-counter.ts` prefers the provider's `/tokenize` endpoint (cached as unavailable on failure) and falls back to `estimateConservativeTokens`; `ConversationRunner` uses real counts for fixed prompts and history trimming, and the compaction notice reports the provider count from `session_before_compact`. The SDK's own compaction trigger cannot be given a token counter — it already uses provider `usage.totalTokens` when available and only estimates trailing messages, which is why tool results are bounded before entering the session. `src/agent/microcompact.ts` registers a `context` extension that shortens older `toolResult` entries before each request (recent 4 kept whole, older ones capped at 400 chars plus a re-read hint) and emits a notice; it changes only the LLM request, not persisted session/trajectory. The SDK compaction reserve is lowered to 1 KiB so its trigger stays near the window; after each `session.prompt()` finishes, `PiAgent` counts the session with the real token counter and calls `session.compact()` itself when it reaches `min(agent.compaction_trigger_percent% of window, window - max_output_tokens - 1 KiB)` (default 85%, runtime setting), attaching the threshold reason to the compaction notice before the compact call. With `agent.compaction_dynamic_threshold` enabled (default), `resolveAdaptiveCompactionThreshold` (`src/agent/adaptive-compaction.ts`) adjusts that threshold by each turn's real token growth — measured against a baseline counted right after history seeding — lowering it when a turn consumes more than 15% of the window and raising it when growth is slow; adjustments are bounded to 10% down / 5% up of the window, smoothed over the last four turns per conversation, and the adaptation is also used in the compaction notice's reported threshold. The two summary layers are unified: if `ModelResponse.compactionSummary` is present (from SDK threshold/overflow compaction), `ConversationRunner.updateSummary` persists that summary directly as the cross-turn rolling summary; it only runs the chunked app-level summary when no compaction occurred and history was trimmed. Compaction summaries use `domainSummaryInstructions` (files/paths, confirmed findings, pending work, rejected approaches) via `generateSummaryWithUsage` with the active model; the bounded deterministic summary remains the fallback when that call fails. `AppStore.contextMetrics` persists compaction (threshold/overflow), microcompacted result counts/chars and real-vs-estimated token counts; `GET /api/ops/overview` exposes them and the admin console shows a Context metrics page.
- Runtime settings are the only supported way to change the model, response language, budgets, tool switches, timeouts, blocked hosts, Skill roots and GitLab connection (base URL and tokens). `src/config/settings.ts` owns the generalized `runtimeSettingDefinitions` (section + field, not just `agent`, and `number` / `boolean` / `string` / `list` types, plus `scale` for seconds→milliseconds and `item` for list validation), `runtimeSettingsView`, `runtimeSettingsEffective`, `applyRuntimeSettings`, `applyRuntimeSettingRows`, `copyRuntimeSettings` and `validateRuntimeSettings`; the Server exposes `GET`/`PUT /api/ops/settings`, stores the submitted set in SQLite `runtime_settings` (`updated_at`/`updated_by`), reapplies it at startup, and writes an `update_settings` audit entry with the operator and the old→new diff. The database is the source of truth after the first save: the config file only supplies initial values, so the console sends every editable key and has no "restore to config file" action. `model` and `response_language` are read per request/turn, so they apply to the next one. Only bootstrap values stay file/environment-only: listen address, storage paths and the fallback model connection values. Users log in with GitLab OAuth2; their encrypted tokens live in `users` and sessions in `user_sessions`. `GET /api/auth/status` is a public 200-only status probe used by the SPA route guard: protected pages render only after it confirms `authenticated` (otherwise the UI redirects to `/auth/gitlab`, or to the setup page when `setupRequired`). API calls keep returning 401 JSON — never 302 — and `src/app/ui/api.ts` turns a 401 into a single client-side redirect to the same destinations. GitLab tokens are stored in `runtime_settings` but never echoed (the UI shows a placeholder and blank input keeps the saved value); `SettingsService.onApplied` reconfigures `GitLabClient`/`GitManager` for the inline conversation runner in the Server so changes take effect immediately. The console `SettingsPage` renders `settingGroups` from `src/app/ui/types.ts`: common groups stay expanded, while window-derived and timing keys live in collapsed advanced groups, and every field shows the effective value returned by the Server when the runtime adjusted it. String fields render a `Select` when the field lists `values`, otherwise an `Input` (`Input.Password` for `secret` fields); list fields render a tag `Select`. The UI field keys must match `runtimeSettingDefinitions` exactly; `test/unit/settings.test.ts` enforces that both directions stay in sync.
- With `agent.auto_context_tune` enabled (default), a recognized provider overflow lowers the effective `contextWindow` only for that fresh-session retry (a structured config override passed to `runSession`); it never writes back the model catalog or mutates shared config. `auto_context_tune` therefore controls session-scoped adaptation, not permanent model changes. Model requests inject a `undici` `fetch` + `Agent` (`headersTimeout`/`bodyTimeout` follow `agent.request_timeout`) because Node's built-in fetch hardcodes a 300s headers timeout that otherwise overrides the configured timeout. `agent.response_stall_timeout` (default 180s, `0` disables) aborts a turn when the model produces no output for that long and streams a waiting notice to the console, so an unresponsive model fails fast instead of spending 20 minutes in SDK retries.

## Architecture and safety invariants

These are deliberate constraints, not incidental behavior. Do not weaken them to make a change simpler.

- Authorization lives in Corvex code: OAuth2 login, per-user GitLab tokens for the console, request body limits, and explicit user intent for every GitLab write. The ops console project scope is controlled by the logged-in user's GitLab token, not a static allowlist.
- Clone and web URLs are derived from the configured `gitlab.base_url` plus GitLab's `path_with_namespace`, never from GitLab's `http_url_to_repo`/`web_url` (those follow the instance's `external_url` and may point at an unreachable internal address). `GitManager` still enforces that the scheme and host match the configured base URL; a mirror whose origin has the same path but an older host is re-pointed instead of re-cloned.
- Every conversation turn pins the branch head SHA and re-verifies that snapshot when preparing the worktree and before GitLab writes. A stale snapshot ends in `stale`, not a partial write.
- The Pi session gets only the tools the turn needs. No built-in `bash`, `edit` or `write`; custom tools confine paths to the conversation worktree and enforce byte limits themselves. Skills are instructions, never access control.
- Conversation turns pin their GitLab target SHA and expose tools derived from the conversation's mode; conversations are uniformly read-write and may publish to GitLab (only through explicit write tools and with clear user intent) and write to the worktree through bounded fs-write tools.
- Agent output is untrusted: GitLab write tools require explicit user intent, target the bound project, and describe irreversible actions. The agent never publishes directly — Corvex re-checks authorization, cancellation and revision before writing to GitLab.
- Never execute repository code, scripts or tests. There is no shell executor by design; adding one requires a separate sandbox and authorization design.
- Conversation turn transitions are enforced in `AppStore` (`queued -> running -> completed`, plus `failed`, `stale`, `cancelled`). Failures are not retried automatically because a GitLab write outcome may be uncertain; conversations may publish only through their explicit write tools.
- Configuration is validated per role: GitLab tokens are optional at startup because they are stored in `runtime_settings`; `storage` commands need only storage settings.

## Tests

- Vitest; `vitest.config.ts` scopes the suite to `test/**` so local runtime data under `data/` (conversation workspaces can contain third-party `*.test.js`) is never scanned. Unit tests sit in `test/unit/<module>.test.ts` next to the module they cover; the ops console scripts have `test/unit/ui-*.test.js`.
- Keep tests hermetic: no outbound network, no dependence on developer machine state, clean up temp dirs, and abort running loops in `afterEach`.
- Add or update tests for behavior changes, including failure paths (invalid model output, expired revision, cancellation, tool scope violation).

## Commits and pull requests

- Conventional commit prefixes are used (`feat:`, `fix:`, `docs:`, `chore:` and scoped variants like `feat(git):`); subjects are written in Chinese or English, matching the surrounding history.
- Keep one logical change per commit and stage only files related to it. Do not commit `.env`, local databases, or `data/`.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, tests, build, then a Docker server smoke test. A tag push (`.github/workflows/release.yml`) publishes the multi-arch GHCR image and a GitHub release, so do not create releases or push tags from a working branch.
