# AGENTS.md

Guidance for coding agents working in this repository. Read `design.md` before making architectural changes: it is the binding contract for the runtime, boundaries and security invariants.

## Project overview

Corvex is a self-hosted GitLab collaboration agent. It is a single TypeScript application running one process that owns one SQLite database and one Git storage root:

- `server`: the only runtime mode. It serves the ops console and executes conversation turns inline through `ConversationRunner`. The ops console authenticates each user through GitLab OAuth2 and discovers projects visible to that user.
- `ConversationRunner` (in-process): claims a turn, pins the repository branch head SHA, reuses the conversation's detached Git worktree, runs one Pi SDK session for that turn, streams its output, and persists the trajectory and final reply. Startup recovers interrupted turns.

The agent runtime is `@earendil-works/pi-coding-agent` (Pi SDK). Pi runs the model loop, tools and skills; Corvex owns authorization, state, validation and GitLab writes. Conversations live in their own `conversations` / `conversation_messages` / `conversation_turns` tables and run inline in the Server. Webhook-driven task events are deferred; see `ROADMAP.md`.

The composer keeps a per-conversation input history in `localStorage` (`src/app/ui/inputHistory.ts`): Up/Down navigate older/newer messages only when the caret is on the first/last line, preserving multiline editing, and Down from the newest restores the in-progress draft. The composer completes slash commands from the **conversation skills** stored in SQLite (no permanent quick-action button row — the `/` menu is the single discovery surface, matching mainstream coding agents). `src/app/conversation-command.ts` only parses the `/name args` shape; `resolveCommandRequest` looks the name up in `conversation_skills`, expands the skill template (using `$ARGUMENTS` or appending the arguments) and returns a short title string. The command name never reaches the model: `ConversationRunner` puts the expanded template in `buildConversationPrompt.currentRequest` and leaves the base system prompt untouched. Skills are managed by admins in Settings → Skills and follow the [Agent Skills specification](https://agentskills.io/specification): a skill is one SKILL.md (YAML frontmatter + single-language Markdown body) edited in a lazy-loaded Monaco editor; `name`/`description` are required, with optional `license`, `compatibility`, `metadata` and `allowed-tools`. Corvex settings live in `metadata.corvex-enabled` (legacy `corvex-quick-action` / `corvex-quick-label` keys are tolerated but no longer drive UI). Administrators can also import **skill packs**: `POST /api/ops/admin/skills/import` accepts a raw ZIP (`application/zip`, hard-capped at 10 MiB via a dedicated Fastify content-type parser) or JSON `{channel: url|github|gitlab, value, ref?, path?, overwrite?}`; `src/agent/skill-import.ts` streams the ZIP with `yauzl` (25 MiB extracted, 1000 files, path-traversal and symlink rejection, only `SKILL.md` parsed) and `src/agent/skill-sources.ts` resolves HTTPS/GitHub codeload/GitLab archive URLs using the signed-in user token. The ZIP is stored unchanged in `skill_packs`; derived skills live in `conversation_skills` with `pack_id`, so toggling or deleting a pack toggles or removes its skills. GitHub/GitLab sources use the same importer, giving one storage shape across upload and remote channels. The seven legacy commands are seeded as editable system skills (disabled or renamed but never deleted). Bundled `scripts/` are intentionally NOT executed — Corvex has no shell executor by design, and `allowed-tools` never widens the tool set (authorization stays in application code). `GET /api/ops/skills` serves enabled skills to every signed-in user; CRUD lives under the admin-only `/api/ops/admin/skills`. Typing `/` shows a vertical, height-capped list of enabled skills with localized descriptions; choosing a command or a welcome prompt inserts text and refocuses the composer via a `Sender` ref.
Conversations are the ops console's primary object: a conversation binds one repository branch and each turn keeps its own trajectory (`conversation_trace` keyed by `turn_id`) and execution records. The console opens on Conversations, renders each assistant reply's thinking and tool calls in the Chat tab through `ConversationTimeline`, syntax-highlights fenced code blocks in replies with `MarkdownCode`/`highlight.js` injected through XMarkdown's `components.code` (inline code stays plain, dark theme overrides live in `theme.css`); markdown tables use GitHub-style borders/header shading/zebra rows scoped under `.conversation-message-markdown`; ```mermaid and ```flowchart fences render through a lazy-loaded `MarkdownDiagram` (Mermaid 11, `securityLevel: "strict"`, theme follows `data-theme`), with the CSP nonce stamped into the SVG style before injection so nonce-based CSP does not strip diagram styling. It shows the conversation's system prompt above the transcript (the server derives it from `agent.response_language` and the conversation mode in `GET /api/ops/conversations/:id`), and reads a single turn's records through `GET /api/ops/conversations/:id/turns/:turnId`; the store verifies the turn belongs to that conversation. Trajectory data stays redacted and size-capped in `src/store.ts`.

The repository name above the conversation is a button that opens `RepositoryInfoPopover` (a click-triggered Ant Design `Popover` anchored `bottomRight` so it never overflows the viewport, not a drawer) with GitLab project metadata from `GET /api/ops/projects/:id` plus the conversation's branch and pinned SHA; project details are prefetched on mount so the popup renders at full size immediately without shifting, and only http(s) `web_url` values become links. Because the popover is portalled to `body`, its content uses the global theme variables; the panel background/text, title color and 340px cap are set through `styles.container` / `styles.title` / `styles.root` with `var(--bg-panel)` / `var(--text)`, so both light and dark modes stay in sync with the console (Ant Design's runtime styles need at least four class selectors to override via CSS). The conversation sidebar groups conversations by repository with the most recently updated conversation (and group) first; each group has a sticky header with a stable color dot and separator, items are single-line titles, and a running turn shows a pulsing dot. Group headers toggle their conversations, and a button placed before the Chat tab in the workspace tab bar collapses the whole conversation list entirely; both states persist in `localStorage` and the width transition matches the main sidebar. Right-clicking an item opens archive/unarchive and delete actions (`POST /api/ops/conversations/:id/archive`, `DELETE /api/ops/conversations/:id`); archived conversations are hidden by default and reachable through a sidebar toggle. Deletion also removes the conversation's worktree and is rejected while a turn is running.

While a turn runs, the Chat tab streams its assistant text so the reply fills in token by token instead of appearing at once. `PiAgent` forwards cumulative text from the SDK's `message_update` events (`onTextDelta`), `ConversationRunner` publishes it per turn with the latest snapshot for late subscribers, and `GET /api/ops/conversations/:id/turns/:turnId/stream` serves it as SSE. The console reads it through `src/app/ui/stream.ts` with `fetch` rather than `EventSource`, because the console's Basic credentials are only attached automatically to same-origin `fetch`. The stream is display-only: it never writes to SQLite, closes with a `done` event as soon as the answer is persisted, and polling remains the fallback when the connection drops. Between every model request and its first output the console shows an animated waiting indicator with elapsed seconds (`ModelWaiting` in `ConversationsPage.tsx`, driven by the pure `resolveWaitingSince` state machine in `src/app/ui/conversationWaiting.ts`): a `reset` text/thinking event starts it, also after each tool settles; real content or a running tool clears it. It replaces the old "only before the first token" check, so multi-round tool loops also show feedback. `resolveWaitingStage` escalates the copy and colors after 15s and again after 60s, so a long wait offers an explicit stop hint.

The same stream carries the model's thinking text as `thinking` events and each tool execution as a `tool` event. The console renders them as one interleaved `ConversationTimeline` above the final reply — a new thinking entry starts on every model round and the following tool calls are appended in execution order, so every thought and every tool call is visible separately. Thinking, intermediate replies and tool calls are folded into a redacted, size-capped process snapshot on `conversation_turns.process`, so the process block survives a reload; redacted thinking parts are skipped in the live stream and tool events carry a call ID for replay. The whole process block is forced open and cannot be collapsed while the turn runs, then collapses as one unit when it settles (the operator may expand it again). Each tool call is itself a small disclosure whose parameters stay hidden until expanded. For conversation tasks the `record_plan` tool records a bounded 3-6 step checklist without an extra model call; the Chat process block renders `record_plan` tool inputs as a numbered plan, and the plan is persisted in the process snapshot. A streaming thinking block (`ThinkingContent` in `ConversationTimeline`) follows new text only while its own scroll position is at the bottom; scrolling up detaches it, using `isAtScrollBottom` from `src/app/ui/scroll.ts`. Long tool-call descriptions keep their head and tail visible with a middle `...`: `fitMiddleEllipsis` measures real glyph widths via canvas and splits evenly, a `ResizeObserver` re-fits on width changes, and the summary wraps so status/duration/parameters never squeeze the name into a few characters; the full text stays in `title`. Context changes are first-class: `PiAgent` consumes SDK `compaction_start`/`compaction_end` (and Corvex's own history-trim retry), records `kind='context'` trace entries (`context.compact` / `context.trim`), and forwards localized notices through `onContextDelta` → SSE `context` → a `conversation-context-notice` segment in the Chat process block; the Trace tab shows context as a third track alongside LLM and tool. The context trace records bounded before/after snapshots: a `session_before_compact` extension captures the messages scheduled for summarization (`buildContextSnapshot`, capped by message/character count), and `compaction_end` stores the resulting summary and first kept entry id; Trace's Context inspector shows both snapshots. The observe extension also emits the start notice as soon as `session_before_compact` fires and reuses one id through success/failure; the start notice explains the trigger (reason, tokens/window percentage, effective threshold) from `session_before_compact`; after one SDK summarization failure it returns a deterministic bounded summary instead of letting the over-limit context trigger the same failing LLM summarization forever. The process uses a lightweight OpenCode-style timeline (left rail, per-step dots, small muted headings, single-line tool rows) rather than stacked cards. A right-side turn rail (`ConversationTurnNav`) shows every user-initiated turn as a slim vertical bar inside a fixed-height rail, so bars shrink as turns accumulate; bars are numbered by turn (matching the Trace tab, not the raw message index) and the rail is anchored 20px right of `.ant-bubble-list .ant-bubble-list-scroll-content` and vertically centered. Hovering shows the summary and date; clicking jumps to that turn. Wheel direction uses a single cross-platform rule from `src/app/ui/turnWheel.ts`: `deltaY` is already normalized by the browser, so scrolling down advances to newer turns on every platform (the old macOS inversion made it backwards). A 150ms `shouldStepTurnWheel` cooldown collapses a trackpad gesture into one step so a single swipe no longer jumps many turns. Each wheel step scrolls the transcript to that user message, and scrolling the transcript updates the active marker. The chat transcript pane is the single scroll container: `Bubble.List`'s internal scrolling is disabled and the pane follows new content only while the user is near the bottom; scrolling more than 160px away from the bottom reveals a floating `Scroll to latest` button that smoothly returns to the newest message (both the threshold and the button state are driven by `handleTranscriptScroll`). Switching workspace tabs or switching conversations always resets the transcript to the latest message, via a `forceScrollToLatest` ref consumed either by the scroll effect or by the pane ref callback when rc-tabs mounts a fresh Chat pane. While a turn is running or queued, the composer's suffix swaps the send button for a `Stop` button that posts `/api/ops/conversations/:id/turns/:turnId/cancel` and clears the local pending state. Desktop notifications are handled by the `useTurnNotifications` React hook (`src/app/ui/useTurnNotifications.ts`) plus the sidebar bell: the first send requests permission, the bell toggles the saved preference, and a turn-completion notification is only raised when the page is hidden or unfocused. A user can also interject while a turn runs: `POST /api/ops/conversations/:id/messages` routes the message through `ConversationRunner.interject` into a per-turn `SteerChannel` (`src/agent/pi.ts`) that binds `session.steer` once the Pi session is ready, so the supplement reaches the model before its next call without creating a new turn or changing the pinned SHA. Messages arriving before the session exists are buffered and drained in order (`setSteeringMode("all")`), and a turn that already settled falls back to a normal queued turn so input is never lost. The same endpoint keeps the idle path unchanged and also accepts `delivery: "queue"` (a durable, reorderable FIFO list in `conversation_followups` that the Runner drains after the turn settles, re-pinning the branch SHA per item and surviving restarts) and `delivery: "interrupt"` (abort the turn, wait for its partial changes to land, then start a fresh turn). The composer shows interject, queue, interrupt and Stop actions while a turn is active, plus a queue panel with reorder/remove. The workspace also has a read-only Git tab (`ConversationGitGraph` + pure `gitGraph.ts` layout): `GET /api/ops/conversations/:id/git/graph` reads the project mirror (`rev-list --parents --topo-order --all`, bounded by limit/offset), highlights the conversation's pinned SHA and `refs/conversations/<id>` commits, draws lanes/merges as SVG beside an antd `Table` (aligned Commit/Date/Author/Hash columns, sortable, with a legend and an author filter backed by `/git/authors` and the graph's `author` query), also resolves lightweight/annotated tags (dereferenced via `for-each-ref`'s `*objectname`, returned in each node's `tags` field and rendered as orange badges/dots), marks the worktree HEAD (and its current branch name when not detached) with a purple `HEAD` badge; the toolbar has Pull and Push-to-ref quick actions (`POST /api/ops/conversations/:id/git/pull` and `/push`, rejected while a turn is running) that fetch from the mirror or save worktree changes to the conversation ref; and expands the selected commit inline under its own row via `GET /api/ops/conversations/:id/git/commit/:sha` to show the full message and bounded patch with on-demand pagination; the SVG row offsets are recomputed from measured item heights so nodes and edges stay aligned with the list after expansion; when an author filter hides a commit's parents, the layout draws a dashed edge to the next visible commit so the history stays visually continuous. The same file list and diffs live in a standalone **Changes** workspace tab (the Git tab shows only the commit graph); both are backed by `GET /api/ops/conversations/:id/git/changes`: it diffs the conversation ref against its parent commit in the mirror and renders a bounded per-file patch list; each expanded patch is shown in a lazily loaded Monaco inline diff editor (`DiffViewer`, sharing `src/app/ui/monaco.ts` setup with `CodeViewer`), with `parseUnifiedDiff` reconstructing the two sides from the hunk and themes following the console theme. The same view can be filtered to one turn via `GET /api/ops/conversations/:id/turns/:turnId/changes`: each saved turn also writes a `refs/conversation-turns/<conversationId>/<turnId>` ref in the mirror so its diff is replayable independently. Deleting a conversation removes the worktree, the conversation ref and every per-turn ref; startup/daily retention prunes orphan refs the same way. The console's "discard changes" action asks for confirmation first, lists the affected paths and offers downloading a `git format-patch` patch before the irreversible deletion. Deriving changes from Git objects (not from recorded fs-write calls) is deliberate: future command-line or external edits will still be detected as long as they land in the worktree/conversation ref. Right-clicking a commit row opens a controlled `Dropdown` (1×1 anchor, outside-click/Escape to close) with copy hash/short hash/subject/author, download patch (standard `git format-patch` mailbox output via `GET .../git/commit/:sha/patch`, saved as `<short-sha>.patch` and directly applicable with `git apply`/`git am`), and "view details" actions. The floating composer starts at three rows (`autoSize`) and its `footer` holds `ComposerModelPicker`, which groups the provider catalog in a borderless `Select`; choosing a model calls the existing activate endpoint, so the switch is global and applies to the next turn (pure grouping/active lookup logic lives in `src/app/ui/modelPicker.ts`). A compact `ContextBrief` sits directly below the composer for existing conversations: it reads only the `/context` summary, shows the latest request's window usage, token counts, threshold and snapshot count, and switches the workspace to the Context tab when clicked; it hides itself when no snapshot exists or the summary cannot be read.

The welcome page's quick prompts come from `welcomePromptGroups(copy)` and render as grouped Ant Design X `Prompts` cards (a category heading plus two questions); clicking a child resolves the full question by key, and the setup pane never auto-scrolls to the bottom. The repository and branch selectors (`.conversation-composer-setup`) sit centered between the welcome text and the grouped prompts, while the floating composer's footer holds only the model picker.

Each conversation carries an explicit mode (`ConversationMode` in `src/model.ts`, default `gitlab`) instead of hardcoded assumptions. `conversationCapabilities(mode)` is the single source for a mode's workflow step, repository writes and GitLab writes; the runner, the Pi prompt and tool access, the store, and the console all derive from it. `src/agent/tool-catalog.ts` injects a `<available_tools>` section into the system prompt via the Pi SDK `before_agent_start` hook, built from `pi.getActiveTools()` and `pi.getAllTools()`: the SDK skips its own tools section when a custom systemPrompt is supplied, so without this the model only has function schemas and can deny having tools when asked. The static prompt tells the model that this section is the sole authority for capability questions (`src/agent/tool-access.ts` is the shared source for the web-tool switches used by registration). The prompt also directs the model to use web_search/web_fetch for time-sensitive facts (so it does not invent current news from training data), to re-read edits with read_file/git_diff before reporting, to follow existing repository conventions without guessing, and to reserve record_plan for multi-step tasks rather than simple questions. The read-only fs set also exposes a bounded `tree` (`readAllowedTree`/`renderDirectoryTree` in `src/agent/fs/read.ts`): 4 levels / 300 nodes / 24 KiB, sorted deterministic output, skips dependency and generated directories, never follows symlinks, and marks `truncated`; the prompt tells the model to call it once to orient instead of repeatedly listing directories. A bounded `glob` (`findAllowedFiles`) finds files by name pattern (`*` within a segment, `**` across directories, `?` for one char), returns paths only with 200-entry / 24 KiB caps. `search_text` stays literal by default with opt-in `regex: true` (200-char patterns, 2 KiB per line matched) so a model that writes `pause\(\)` gets an explicit hint to search literally instead of silent zero matches; `git_grep` remains literal. Its authorization wording treats the user request as consent for in-scope actions and explicitly forbids stopping to ask for routine approval; write-tool descriptions no longer say "only on explicit user request". `src/agent/project-guidance.ts` reads `AGENTS.md` (or `AGENTS.override.md`) from the pinned worktree root each turn and injects it through the SDK `agentsFilesOverride` as `<project_instructions>`; default-on via `agent.project_agents_md`, byte-capped by `agent.project_agents_md_max_bytes`, framed as untrusted repository data that cannot override the system prompt or the current request. v1 is root-only; nested AGENTS.md is a later increment. Web tools are split: `web_fetch` (`src/agent/web-read.ts`) handles HTML, JSON (including `+json` vendor types, validated then pretty-printed), plain text and XML with a 1 MiB text budget, while `web_download` (`src/agent/web-download.ts`) writes binary/large files up to 16 MiB into `.corvex/downloads/` in the pinned worktree; both share SSRF guards, DNS pinning and redirect revalidation via `fetchWebResponse`, and refuse private/reserved/blocked hosts. Downloads never overwrite repository files and refuse executable/installer extensions because Corvex has no shell and downloaded bytes are untrusted. Conversations are uniformly read-write: `gitlab` (the only mode) reads the repository and adds the full bound GitLab tool set from `src/agent/gitlab/` (`issue.ts` and `merge-request.ts`, combined in `index.ts`): discovery/reads (`get_project_info`, `list_*`, `get_*`, `get_merge_request_changes`, paginated `get_merge_request_commits`, discussions), Issue lifecycle (create/update/close/reopen/delete plus note create/update/delete) and MR lifecycle (create/update/close/reopen/merge/delete, approve/unapprove, note create/update/delete, resolve discussions), repository file edits go through the bounded fs-write tools, and `gitToolset: true` also enables the consolidated `src/agent/git/` tool set (`inspect.ts`: git_status/log/show/diff/branches; `workspace.ts`: git_clone/branch/checkout/pull/merge (git_checkout switches to a local branch or tracks origin/<name> before an MR); `changes.ts`: git_commit/push/publish/push_branch/rebase/cherry_pick/revert; combined in `index.ts`). All Git tools are bound to the conversation's worktree and local project mirror: no arbitrary URL/remote/force option. `git_push` writes `refs/conversations/<id>` in the mirror; `git_publish` saves the current changes and fast-forwards the resulting commit to a named GitLab branch in one call (no SHA to remember), so a merge request can show a real diff. `git_push_branch` is the lower-level variant for an already known SHA. Both never force-push and are used as the task requires. All GitLab tools are fixed to the conversation's project, iids must come from the user or a read result, and write tools are bound to the conversation project; irreversible or public actions (delete/merge/approve) say so in their descriptions. Adding a mode means extending `conversationCapabilities`, the prompt and tool wiring, then updating docs.

Each conversation keeps one worktree reused across its turns (`workspaces/<projectId>/conversation-<conversationId>`, derived by `conversationWorkspaceName`) instead of preparing and deleting one per turn. `ConversationRunner` owns the cache (idle TTL plus an LRU cap, released on Server shutdown and swept again on every startup so a crash cannot accumulate worktrees); `GitManager.prepareConversationWorkspace` re-verifies HEAD for the same pinned SHA and only `checkout --detach`s when the snapshot advanced, so the fixed-SHA invariant still holds. Conversations write to the worktree only through the bounded fs-write tools or the bound Git tool set, and are serialized per conversation, which is what makes reuse safe; branch/merge/rebase/cherry-pick/revert tools are validated; rebase/cherry-pick run only on a clean worktree and abort automatically on conflicts, and no tool force-pushes. Git mirrors are also fetched lazily: `prepareConversationWorkspace` runs `cat-file -e` first and only fetches the SHA when it is missing. `fetchFromMirror` fetches by the mirror filesystem path (not the `origin` remote name) with explicit refspecs into `refs/remotes/mirror/*` and `refs/remotes/origin/*`: linked worktrees inherit the mirror's `remote.origin.mirror`/`+refs/*:refs/*`, which otherwise makes git refuse to update a checked-out branch. `git_sync` (`syncMirrorFromGitLab`) refreshes GitLab branch tips into `refs/corvex/remote/*` (never `refs/heads/*`, which worktrees may have checked out), and `pushBranchToGitLab` calls it before pushing and rejects non-fast-forward with an actionable "rebase onto origin/<branch>" message. `git_merge` requires a clean worktree and `git_show` explains when a SHA is not reachable from the pinned revision. `rebaseWorktree` accepts both a bare branch name and `origin/<branch>` (no double prefix). The system prompt spells out the recovery order for non-fast-forward pushes (git_sync → git_pull → git_rebase onto origin/<branch> → retry) and forbids push/branch/commit retry loops; a clean `git_commit` result explicitly tells the model not to repeat the same message. `saveConversationChanges` detaches the worktree HEAD at the saved commit (via `checkout --detach`, never `reset --hard`, so a checked-out branch is never rewritten), making the worktree immediately clean so rebase/merge/cherry-pick can run and duplicate commits are impossible; when a clean detached HEAD has advanced past the conversation ref (rebase/merge/cherry-pick), the ref and per-turn ref are advanced to HEAD so the next turn does not rebuild from the stale ref. `withGitToolBudget` (`src/agent/git/budget.ts`) wraps every model-invoked Git tool with a shared per-turn call counter (`agent.git_tool_call_limit`, default 40, 0 disables; failed calls count), and exhausted budgets force a report instead of a failed-command loop. The turn snapshot (`conversation_turns.head_sha`) stays immutable and is only the stale guard; a separate mutable `conversations.base_sha` is the parent of local unpublished changes and the baseline for Changes/`git_show`. `base_branch` records which branch that baseline came from: `resolveTurnBaseSha` (`src/app/conversation-base.ts`) only follows the remote snapshot when the baseline is on the target branch and there are no unpublished changes, so a feature-branch publish is not lost on the next turn. Any successful `git_publish` / `git_push_branch` advances `base_sha` + `base_branch` and the in-memory `workspace.headSha` and clears the conversation ref (`clearConversationChangesRef`, turn refs kept), so a second commit/publish in the same turn is a fast-forward instead of a non-fast-forward loop. Console git shortcuts also use `base_sha` rather than the last turn snapshot. The first publish to a feature branch reuses or creates an MR through `ensureMergeRequest` (`agent.auto_create_merge_request`, default on, signed-in user token); the prompt forbids the model from calling `create_merge_request` itself to avoid duplicates. A stale turn writes a `context` trace `stale.branch_conflict` via `buildStaleConflictNote` (`src/app/stale-conflict.ts`), using `GitLabClient.getCommit` for the author/title so the Trace tab shows who moved the branch. `buildGitEnvironment` strips inherited `GIT_ASKPASS`/`VSCODE_GIT_ASKPASS_*`/`SSH_ASKPASS` and keeps `GIT_TERMINAL_PROMPT=0`, so missing GitLab credentials make clone/fetch fail fast instead of blocking on an interactive askpass prompt (which previously made turns appear stuck and uninterruptible). Network git operations are bound to the **logged-in user**, not the host or global service settings: `conversation-runner` passes `gitlab.authToken` (the single user OAuth token) into `prepareConversationWorkspace`, `fetchFromMirror` and the Git tools, which thread it as an explicit `authToken` through `ensureCommit`/`ensureMirror`/`runWithRetry`/`pushBranchToGitLab`/`publishToGitLabBranch`; `buildGitEnvironment` puts it in `http.extraHeader`. The per-turn abort `signal` is now also passed into workspace preparation so cancel interrupts git immediately. `storage cleanup` skips conversation workspaces whose conversation still has a queued or running turn (`AppStore.activeConversationIds`), and keeps mirrors for any project referenced by a conversation (`AppStore.pendingProjectIds`) so a later follow-up does not re-clone the whole repository. The workspace TTL/cap and retention days are runtime settings editable in the ops console; eviction never touches queued or running conversations (a removed idle worktree is simply rebuilt on the next turn). Cleanup runs are recorded in `storage_cleanup_log` and shown, 10 per page, in the Storage tab of the Settings page, which is split into Basics / Model / GitLab / Storage / Advanced tabs. The Model tab manages model providers: each provider stores a name, Base URL and API key, and lists its models with their own context window and max output tokens; one model is active globally, the first model added is activated automatically, and selection is applied to the config on Server startup (legacy `model` / `model_base_url` / `model_api_key` runtime overrides are migrated into a provider, and the previous single-table `model_profiles` list is split into `model_providers` + `provider_models`). The API key is never returned by the API or written to audit logs (an empty password field keeps the saved value), so the SQLite file and its backups must be protected. Each settled assistant reply's actions row starts with the Copy button, followed by generation TPS, elapsed turn duration, and the producing model label. TPS and duration are computed in `AppStore.getConversation` from successful LLM traces (`generation_duration_ms`) and the turn's created/updated timestamps, so the Chat tab needs no extra request. The label uses the settings provider's display name (`applyActiveModel` copies it to `agent.providerName`) plus the model ID; the Pi SDK's internal `corvex-openai-compatible` provider ID is never shown (`displayModelName` strips it from older rows, in both the transcript and Trace).

## Environment

- Node.js 26.12.1 (`.nvmrc`, `engines.node`) and pnpm 12.4.1 (`packageManager`). Do not switch package manager or edit `pnpm-lock.yaml` by hand; keep the `allowBuilds` entries in `pnpm-workspace.yaml`.
- Install with `pnpm install --frozen-lockfile`.
- `git` must be on `PATH`: the inline conversation runner shells out to Git, and unit tests build real repositories.
- SQLite comes from Node's built-in `node:sqlite`. Never add a database driver, ORM or query builder.

- `init --config <path>` writes a config template; `check-config --config <path> [--for server|storage]` validates per role.
- `server` starts the single process (HTTP and inline conversations).
- `backup --database <path> --output <new-path>`; `storage cleanup [--older-than-days n] [--apply]` (dry run unless `--apply`).

`Makefile` targets (`build`, `test`, `lint`, `typecheck`, `run`, `init`, `config-check`, `deploy`) are thin wrappers around the same commands.

Before finishing a change, run `pnpm run lint`, `pnpm run typecheck` and `pnpm test`; CI runs them on Ubuntu, macOS and Windows, so keep paths and file handling cross-platform.

## Code conventions

- ESM with `module`/`moduleResolution` `NodeNext`: relative imports carry a `.js` extension even from `.ts` files (`./model.js`). Use `import type` / `type` modifiers for type-only imports.
- TypeScript is `strict`. Avoid `any`; validate external data (YAML, HTTP bodies, GitLab payloads, model output, SQLite rows) at the boundary and narrow with type guards.
- Prefer Node built-ins (`node:fs/promises`, `node:crypto`, `node:sqlite`, `node:timers/promises`) and standard `fetch`. The HTTP layer uses Fastify (`src/app/http`: `server.ts` lifecycle plus `auth.ts`, `routes.ts`, `respond.ts` and per-area route modules), justified in `design.md`; it keeps every request body as a raw Buffer, `/api/ops` validates `content-type` and parses JSON itself, and SSE hijacks the raw response. Preserve the existing status codes, bodies, headers, auth realm and log keys when changing routes. New runtime dependencies are an architecture decision: justify them in `design.md` and keep the dependency set minimal.
- Source comments and JSDoc are written in Chinese; keep that convention and keep them true. Identifiers and user-visible log keys are English.
- User-visible text follows the configured `agent.response_language` (`en` or `zh-CN`). Docs are bilingual: `docs/<page>.md` plus `docs/zh-CN/<page>.md`, and `README.md` plus `README.zh_CN.md`, with navigation in `docs/.vitepress/config.mts`. Update both languages when behavior, config, or operations change.
- No secrets in code, configs, fixtures, logs, prompts or trace payloads. Trace data is redacted and size-capped in `src/store.ts`; do not bypass that path. `src/redact.ts` owns the shared rules (`redactSensitiveText`, `sanitizeSensitiveValue`, `sanitizeSensitiveText`): `startTrace`/`finishTrace` now sanitize pre-stringified `trace_input`/`trace_output`/`raw_content`/`error_detail` at the storage boundary (structural JSON redaction for stringified objects, text regex otherwise, then a 64 KiB cap), and `saveConversationSummary` redacts model-generated summaries. `buildContextSnapshot` redacts tool-result text before it can enter a compaction trace or the Trace inspector, and `PiAgent` redacts compaction summaries before reusing them as the cross-turn rolling summary.

- Context governance lives in `src/agent/budget.ts` (`estimateTokens`, `estimateConservativeTokens`, `resolveMaxInputTokens`, `resolveHistoryBudgetTokens`, `chunkForSummary`, `isContextOverflowError`, `trimHistory`), `src/agent/tool-budget.ts` and the `agent.*` budget keys (`context_window`, `max_input_tokens`, `history_token_budget`, `turn_tool_result_bytes`, `compaction_*`, `summary_enabled`). Repository-file tools reject absolute worktree paths at the tool boundary (`requireRelativeRepoPath`; absolute paths are only accepted for trusted skill roots) and the system prompts require repository-relative paths, so worktree paths never leak into trajectories. Tool results are hard-truncated per call and per assistant round before they enter session history, and the compaction reserve still covers a **full** tool-result round plus `max_output_tokens` and a fixed margin; the round bound itself scales to 25% of the context window (4 KiB floor, 128 KiB cap), and an explicit `compaction_reserve_tokens` is capped at 25% of the window (default `0`, i.e. derived) so a 32k window compacts around 62.5% instead of 50% while still leaving room for a maximal tool round before the next request. `turn_tool_result_bytes` stays a soft checkpoint, not a hard cap: at 75% the model is steered to record progress and use targeted reads, but the turn is not aborted; context growth is absorbed by SDK compaction and a single history-dropping retry on a provider overflow. `session.prompt()` resolves normally when the provider rejects a request, so `runSession` records the final assistant message's `errorMessage` and rethrows it: without that, a failed turn would return the previous turn's reply (the last assistant message in the session) as a fresh answer and the overflow retry would never fire. Requests are trimmed locally before they leave the process; do not widen these budgets to paper over a provider error. `resolveMaxPromptBytes` derives the per-request prompt cap from `context_window` rather than a fixed 96 KiB, so long history is not rejected before it leaves the process. `src/agent/token-counter.ts` prefers the provider's `/tokenize` endpoint (cached as unavailable on failure) and falls back to `estimateConservativeTokens`; `ConversationRunner` uses real counts for fixed prompts and history trimming, and the compaction notice reports the provider count from `session_before_compact`. The SDK's own compaction trigger cannot be given a token counter — it already uses provider `usage.totalTokens` when available and only estimates trailing messages, which is why tool results are bounded before entering the session. `src/agent/microcompact.ts` registers a `context` extension that shortens older `toolResult` entries before each request; it changes only the LLM request, not persisted session/trajectory. To stop the model from confabulating about its own past actions, each fresh session injects a bounded "tool evidence" section into the user prompt: `buildToolEvidence` (`src/agent/tool-evidence.ts`) formats the real tool calls/results of the last 10 history turns from `AppStore.getToolEvidence`, capped at 12 tools per turn / 240 chars per field / 12 KiB total, and `ConversationTurnContext.history` carries each assistant message's `turnId`. Facts and claims about history have hard prompt rules: verify past actions with a read tool, and use URLs only verbatim from tool results. A deterministic guard (`src/agent/claim-verification.ts`) checks the final answer for high-risk claims (publish/comment/merge/approve/delete) against this turn's tool trace and emits a `context` notice into the process snapshot when a claim has no matching tool call, so prompt guidance is backed by code. The real cross-turn fix is full session persistence: `conversation_sessions` stores the complete Pi `FileEntry[]` (header + tool use/result messages, capped at 4 MiB) after each successful turn; the next turn restores it via `SessionManager.inMemory(cwd, options, entries)` and skips text-history seeding, so the model sees its actual past tool calls rather than only what it said. Conversation deletion and retention prune these rows. When the payload exceeds the cap, `boundSessionEntries` (`src/agent/session-persistence.ts`) keeps the active branch from the last compaction checkpoint plus the newest contiguous messages instead of dropping persistence entirely, logging the number of dropped entries; a single oversized entry still falls back to skipping persistence. For long autonomous tasks, `src/agent/tool-loop.ts` records bounded tool-call signatures per session and injects a localized steer when the same call repeats (4 consecutive / 8 total) or a tool fails 3 times in a row. `record_plan` is now a persisted task checklist (`conversation_plans`, `ConversationPlan` with pending/in_progress/completed steps); the model can rewrite the list with `steps` or update progress with `updates: [{index,status}]`, and the console renders step statuses. See ROADMAP.md for the remaining long-task gaps. `src/agent/task-budget.ts` enforces soft per-task ceilings (`agent.task_max_rounds` / `task_max_output_tokens`) by steering the model once to wrap up at the limit. `claim-verification` also treats "fixed / completed" as high-risk claims requiring a read-back (`read_file`) or diff (`git_diff`) tool in the turn trace. `maxOutputTokens` has no fixed cap: it is only required to be smaller than the model context window, enforced consistently in config, settings relations and both model APIs with a specific error message. Thinking budgets (`resolveThinkingBudgets`) are set below the output ceiling minus answer room; if the model still spends the whole output budget on reasoning and returns no text, `EmptyCompletionError` triggers one retry at a lower thinking level (`lowerThinkingLevel`, e.g. medium→low) instead of failing the turn. Reasoning is enabled by default (`agent.reasoning_enabled`, runtime setting) — the Pi model is declared with `reasoning: true` and the session gets `thinkingLevel: "medium"`, so the model actually reasons between calls instead of always running with `thinkingLevel: "off"`; operators can disable it for models that do not support reasoning. Users can pick a per-user `thinkingLevel` (off/minimal/low/medium/high/xhigh/max) from a second Select beside the composer model picker; `user_thinking_levels` persists it and the runner clones the config with that level (plus the user model) before creating the turn's PiAgent, while admin `reasoning_enabled` remains a global master switch. `resolveMicrocompactPolicy` derives keep-recent (4–24, scaled by window), kept chars (400/2,000 by window) and a trigger token count (compaction threshold minus 15 percentage points) so a lightly used large window is left completely untouched. Dedupe uses stable `toolCallId`/content hashes instead of message indices, and `onPruned` reports only identities newly entering the pruned set, so repeated per-request rewrites neither spam notices nor inflate `contextMetrics`. `read_file` adds a bounded repeated-read hint after the same path is read five times in one session to discourage the re-read loop that over-aggressive truncation can cause; the console merges same-kind context notices into one timeline entry with a repeat count. The SDK compaction reserve is lowered to 1 KiB so its trigger stays near the window; after each `session.prompt()` finishes, `PiAgent` counts the session with the real token counter and calls `session.compact()` itself when it reaches `min(agent.compaction_trigger_percent% of window, window - max_output_tokens - 1 KiB)` (default 85%, runtime setting), attaching the threshold reason to the compaction notice before the compact call. With `agent.compaction_dynamic_threshold` enabled (default), `resolveAdaptiveCompactionThreshold` (`src/agent/adaptive-compaction.ts`) adjusts that threshold by each turn's real token growth — measured against a baseline counted right after history seeding — lowering it when a turn consumes more than 15% of the window and raising it when growth is slow; adjustments are bounded to 10% down / 5% up of the window, smoothed over the last four turns per conversation, and the adaptation is also used in the compaction notice's reported threshold. The two summary layers are unified: if `ModelResponse.compactionSummary` is present (from SDK threshold/overflow compaction), `ConversationRunner.updateSummary` persists that summary directly as the cross-turn rolling summary; it only runs the chunked app-level summary when no compaction occurred and history was trimmed. Compaction summaries use `domainSummaryInstructions` (files/paths, confirmed findings, pending work, rejected approaches) via `generateSummaryWithUsage` with the active model; the bounded deterministic summary remains the fallback when that call fails. `AppStore.contextMetrics` persists compaction (threshold/overflow), microcompacted result counts/chars and real-vs-estimated token counts; `GET /api/ops/overview` exposes them and the admin console shows a Context metrics page. `src/agent/context-inspect.ts` adds a per-request layer: a Pi `context_with_system` extension classifies the full prompt into system / tools / user / inject / assistant / tool results and emits a bounded snapshot through the `contextSnapshot` hook; the default tap in `ConversationRunner` writes it to `conversation_context_snapshots` (redacted previews, 128 KiB items, newest kept, 300 per conversation). The conversation workspace's Context tab reads `GET /api/ops/conversations/:id/context` (summary) and `.../context/:seq` (full items) and shows window usage, a composition bar, a request timeline, a per-item browser and context events; all sections follow the selected request. Collection is controlled by `agent.context_inspect_enabled` / `context_inspect_max_items` / `context_inspect_max_preview_chars` so the token-counting call can be disabled.

Only bootstrap values stay file/environment-only: listen address, storage paths and the fallback model connection values. Users log in with GitLab OAuth2; their encrypted tokens live in `users` and sessions in `user_sessions`. `GET /api/auth/status` is a public 200-only status probe used by the SPA route guard: protected pages render only after it confirms `authenticated` (otherwise the UI redirects to `/auth/gitlab`, or to the setup page when `setupRequired`). API calls keep returning 401 JSON — never 302 — and `src/app/ui/api.ts` turns a 401 into a single client-side redirect to the same destinations. There are no shared GitLab PAT settings or environment fallbacks: every API/Git call constructs a client from the signed-in user OAuth token, and `SettingsService.onApplied` only updates the GitLab base URL used for mirror origin validation. The OAuth client secret is the only GitLab secret in `runtime_settings` and is never echoed. A one-time migration deletes legacy `gitlab_read_token` / `gitlab_token` rows from existing databases. The console `SettingsPage` renders `settingGroups` from `src/app/ui/types.ts`: common groups stay expanded, while window-derived and timing keys live in collapsed advanced groups, and every field shows the effective value returned by the Server when the runtime adjusted it. String fields render a `Select` when the field lists `values`, otherwise an `Input` (`Input.Password` for `secret` fields); list fields render a tag `Select`. - With `agent.auto_context_tune` enabled (default), a recognized provider overflow lowers the effective `contextWindow` only for that fresh-session retry (a structured config override passed to `runSession`); it never writes back the model catalog or mutates shared config. `auto_context_tune` therefore controls session-scoped adaptation, not permanent model changes. ## Architecture and safety invariants

These are deliberate constraints, not incidental behavior. Do not weaken them to make a change simpler.

- Authorization lives in Corvex code: OAuth2 login, per-user GitLab tokens for the console, request body limits, and tool binding to the conversation's project/worktree. The user's request is the authorization for in-scope work; there are no per-action approval prompts. The ops console project scope is controlled by the logged-in user's GitLab token, not a static allowlist.
- Clone and web URLs are derived from the configured `gitlab.base_url` plus GitLab's `path_with_namespace`, never from GitLab's `http_url_to_repo`/`web_url` (those follow the instance's `external_url` and may point at an unreachable internal address). `GitManager` still enforces that the scheme and host match the configured base URL; a mirror whose origin has the same path but an older host is re-pointed instead of re-cloned.
- Every conversation turn pins the branch head SHA and re-verifies that snapshot when preparing the worktree and before GitLab writes. A stale snapshot ends in `stale`, not a partial write.
- The Pi session gets only the tools the turn needs. No built-in `bash`, `edit` or `write`; custom tools confine paths to the conversation worktree and enforce byte limits themselves. Skills are instructions, never access control.
- Conversation turns pin their GitLab target SHA and expose tools derived from the conversation's mode; conversations are uniformly read-write and may publish to GitLab (only through explicit write tools and with clear user intent) and write to the worktree through bounded fs-write tools.
- Agent output is untrusted: GitLab write tools are bound to the conversation's project and describe irreversible actions for the model's benefit; the harness re-checks authorization, cancellation and revision before writing to GitLab. The system prompt tells the model to act autonomously within bound tools, confirm targets with read tools before risky writes, and recover via a safer path after a denial instead of stopping for approval.
- Never execute repository code, scripts or tests. There is no shell executor by design; adding one requires a separate sandbox and authorization design.
- Conversation turn transitions are enforced in `AppStore` (`queued -> running -> completed`, plus `failed`, `stale`, `cancelled`). Failures are not retried automatically because a GitLab write outcome may be uncertain; conversations may publish only through their explicit write tools.
- Configuration is validated per role: GitLab credentials are never required at startup because calls use the signed-in user token; `storage` commands need only storage settings.

## Tests

- Vitest; `vitest.config.ts` scopes the suite to `test/**` so local runtime data under `data/` (conversation workspaces can contain third-party `*.test.js`) is never scanned. Unit tests sit in `test/unit/<module>.test.ts` next to the module they cover; the ops console scripts have `test/unit/ui-*.test.js`.
- Keep tests hermetic: no outbound network, no dependence on developer machine state, clean up temp dirs, and abort running loops in `afterEach`.
- Add or update tests for behavior changes, including failure paths (invalid model output, expired revision, cancellation, tool scope violation).

## Commits and pull requests

- Conventional commit prefixes are used (`feat:`, `fix:`, `docs:`, `chore:` and scoped variants like `feat(git):`); subjects are written in Chinese or English, matching the surrounding history.
- Keep one logical change per commit and stage only files related to it. Do not commit `.env`, local databases, or `data/`.
- CI (`.github/workflows/ci.yml`) runs lint, typecheck, tests, build, then a Docker server smoke test. A tag push (`.github/workflows/release.yml`) publishes the multi-arch GHCR image and a GitHub release, so do not create releases or push tags from a working branch.
